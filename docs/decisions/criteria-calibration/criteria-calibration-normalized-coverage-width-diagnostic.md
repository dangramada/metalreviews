# Normalized coverage width — does a relative threshold free the four stuck shapes?

**Status: diagnostic only, 2026-08-25. No production code changed. `MAX_VALUE_RANGE_FOR_COVERAGE`,
`isDegreeCoverageComplete` and `elicitationDriver.ts` are untouched, per the brief. Nothing was
written to Supabase; the one DB access is a read-only select of B71's answer log.**

Branch: `criteria-calibration-normalized-coverage-width-diagnostic`.

---

**Headline: the usable threshold window is EMPTY, for both normalization candidates, on the full
12-trajectory evidence set. Not "empty at the tolerance we chose" — empty in the strong sense: no
threshold on either candidate frees even ONE of the four stuck shapes while the healthy traces
still complete at anything like their current round.**

**The failure is structural, and it is a different structure for each candidate:**

- **C1 (`width / widthAtFirstTouch`) cannot fire at all.** On the healthy traces most free
  variables are BORN narrow — 16 to 19 of 24 arrive at first touch already at width 0.167 or
  0.200, at or below today's absolute gate, and then never shrink further, so their C1 ratio sits
  at exactly 1.000 forever. C1 punishes precisely the variables that were determined from the
  start. Any threshold below 1.0 blocks the healthy traces; at or above 1.0 the test is inert.
- **C2 (`width / meanWidthOfTouchedVars`) fires, but only by ceasing to measure width.** It is
  scale-free by construction, so it reports DISPERSION, not determinacy: a model where every
  variable is equally undetermined has every ratio at 1.0 and passes any threshold above 1. The
  lowest threshold that frees all four stuck shapes is **3.35**, and at 3.35 every one of the 12
  traces completes at exactly the round its degree-scoped touch test alone is satisfied — the
  width test contributes nothing. That is Option C (touched-only), which the brief excludes.

**Verdict: negative. The `MAX_VALUE_RANGE_FOR_COVERAGE = 0.2` absolute gate stays as it is, and
§2d's four stuck shapes remain a real, unresolved cost. The UX route (Option D) is the remaining
path. Stage 3b (full re-simulation) was never reached, because nothing survived stage 3a.**

This is the third empty-window result in this cluster, after
`criteria-calibration-accuracy-threshold-recalibration.md` §6 (six quality bars, six empty
windows) and `criteria-calibration-escalation-signal-candidates.md` §6 (five signal variants).
The brief warned against assuming normalization escapes that fate. It does not — see §6 for why
the reason here is genuinely a different one, not a restatement of Candidate A.

## 1. Method

### 1a. What was re-simulated, and why re-simulated at all

The committed trajectory CSVs carry per-round solved POINT vectors. Feasible-range width per
variable is a property of the feasible intervals, which a point vector cannot recover — the same
reason `criteria-calibration-degree-tiers-and-progress.md` §1 gave for re-simulating rather than
post-processing. So the widths were regenerated by replay.

Per the brief, this reused the existing harness instead of writing a new driver:
`scripts/degree-tier-recon-2026-08-18.ts` already computes the per-variable feasible width every
round and then discards it into the `covered` / `touched` / `narrow` / `softFill` aggregates. It
gained one opt-in flag, `RECON_EMIT_WIDTHS=1`, which writes a SECOND CSV
(`normalized-coverage-widths-2026-08-25.csv`, 22 680 rows = 945 rounds x 24 free variables) and
changes nothing else. Verified: the run that produced the widths also rewrote
`degree-tier-recon-2026-08-18.csv`, and `diff` against the committed copy is **byte-identical**.

Evidence set: the fixed 12 of this cluster — oracles `#1`-`#10` plus real sessions `A70` (from the
committed pre-reset backup) and `B71` (read-only select, `RECON_INCLUDE_B71=1`). Nothing added.

### 1b. The two candidates, as implemented

| candidate | normalized width                          | grid                                |
| --------- | ----------------------------------------- | ----------------------------------- |
| C1        | `width / widthAtFirstTouch`               | 0.02 -> 0.98, step 0.02 (49 cells)  |
| C2        | `width / meanWidthOfTouchedVarsThisRound` | 0.05 -> 5.00, step 0.05 (100 cells) |

Two implementation choices worth stating, because they could each be made differently:

- **C1's "first touch" is degree-scoped.** The live gate's touch test is degree-scoped (the
  2026-08-11 fix), so the denominator is the variable's width at the first round it was touched
  AT THE DEGREE BEING JUDGED. Borrowing the denominator from a lower degree would measure a
  narrowing that the degree in question did not do. For the four stuck traces this is moot —
  all 90 of their rounds are degree 2.
- **C2's denominator is the mean over ALL touched variables**, not over "touched and not yet
  finished" as the brief phrased it. That phrasing is circular: which variables count as finished
  is exactly what the threshold decides. The fixed-point variant is C2b, which the approved plan
  gated on C2 showing signal. It showed none — see §6c.

The grid for C2 was extended past the brief's 2.00 to 5.00. Not out of hope: §6 shows the stuck
traces carry worst-variable ratios up to 4.66, so stopping at 2.00 would have reported "never"
without saying how far away "ever" is. The extension is what makes the 3.35 number in §4
reportable.

### 1c. Stage 3a / 3b split, and why the table has a validity rule

The coverage rule is causal: a threshold that ends degree 2 earlier changes every question asked
afterwards, so post-processing the widths of a 0.2-generated run is exact only up to the point of
first divergence. The split approved in the plan:

- the **four stuck oracles** never escalate, so the gate never perturbs them — all 90 rounds are
  exact;
- **A70 / B71** replay a FIXED human answer log, so the gate cannot perturb them either — exact
  throughout;
- the **six healthy oracles** are exact up to and including their real degree-2 boundary round;
  any candidate completing later than that is flagged `needs_resim` rather than reported as fact.

Stage 3b (full re-simulation under a surviving candidate rule) was to run only on thresholds that
survive 3a. **None did**, so 3b was not run. Nothing in §4's verdict rests on a post-processed
number from a diverged region: the four stuck traces' "never" cells and the healthy traces' EARLY
completions are all inside the exact window.

### 6a. Why C1 fails: healthy variables are born narrow and never move

On `#1`, `#8`, `#9`, `B71`, 18 of 24 free variables have `width == widthAtFirstTouch` to three
decimals — width 0.167, already below today's 0.2 gate the moment they are first touched, and flat
thereafter. `#3` has 19 such variables at 0.200, `A70` has 16. Their C1 ratio is 1.000 forever.

This inverts the intended meaning. C1 asks "how much has this variable narrowed since we started
watching it", and a variable that arrived fully determined answers "not at all" — the same answer
a completely stuck variable gives. The stuck traces' worst variables sit at C1 = 0.992-0.997,
which is BELOW the healthy traces' 1.000. C1 does not merely fail to separate the two populations;
it orders them backwards. Hence 0.02-0.88 all-never, and a threshold >= 1.0 that accepts anything
which has not actively WIDENED.

### 6b. Why C2 fails: a scale-free ratio measures dispersion, not determinacy

C2 divides out the very quantity the gate exists to bound. A model in which all 24 variables are
equally undetermined (every width 1.0) has every C2 ratio at exactly 1.0 and passes any threshold
above 1 — which is why the C2 column starts firing at 1.30-1.40, before any stuck shape moves, and
why the healthy traces begin completing tens of answers early (`#10` at 40 instead of 77 by
C2 = 1.60). The stuck shapes resist not because their widths are large in absolute terms but
because they are HETEROGENEOUS: `#6 back-loaded` has a mean width of 0.170 — narrower than `#5`,
narrower than `#2` — while carrying one variable at 0.794, a 4.66x outlier. Freeing that outlier
needs a threshold of 3.35, and at 3.35 the ratio test can no longer fail for any variable in any
trace (§5).

### 6c. Is this the same wall as Candidate A?

Related but not identical, and the distinction matters for what to try next.
`criteria-calibration-escalation-signal-candidates.md` §7 rejected absolute coverage width because
it "is not comparable across users" — a CALIBRATION problem, which is exactly what normalization
is supposed to fix. Normalization does fix comparability: C2's max ratio lands in 1.25-1.38 for
every healthy trace, a genuinely tight band across very different sessions. The window is still
empty because comparability was not the binding constraint. The binding constraint is that the
four stuck shapes have one or two variables the elicitation never constrains at all, and no
rescaling of an unconstrained width makes it constrained. Both candidates confirm §2d's own
diagnosis rather than overturning it: `touched` reaches 24/24, `narrow` does not, and the reason is
missing evidence, not a mis-scaled ruler.

**C2b (fixed-point denominator over "touched and not yet finished") was not run**, per the
approved gate — C2 showed no signal at any threshold below the degeneracy point. It is also
directionally worse: as variables finish and leave the denominator, the mean shrinks toward the
stubborn survivors, so each remaining variable's ratio RISES over the round it would need to fall.
C2b makes the stuck traces harder to complete, not easier.

## 8. What NOT to change on the strength of this document

- **Do not raise `MAX_VALUE_RANGE_FOR_COVERAGE`.** Untested here; this diagnostic covers relative
  rules, not a re-tuned absolute one. §2's reference column is the only absolute-gate evidence it
  produces.
- **Do not read C2 @ 3.35 as a recommendation.** §5 shows it is Option C wearing a ratio, and
  Option C is out of scope by the brief's own exclusion.
- **Do not treat `#2`/`#4`/`#5`/`#6` as "solved-if-we-normalise".** They are not stuck on scale.
  They are stuck on a variable the elicitation never constrains, which is a question-selection or
  UX problem, not a threshold problem.
- **No implementation follows from this document in either direction** — the verdict is negative,
  and the brief forbids implementing even a positive one without a separate brief.
